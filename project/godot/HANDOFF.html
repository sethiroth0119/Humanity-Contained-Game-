Humanity Contained
→ Godot Engine

A complete porting kit for the prototype: GDScript ports of every system, Resource-driven content authoring (items, weapons, enemies, recipes), an iso math library, and a scene-tree blueprint you can recreate in the editor in under an hour.

The prototype was deliberately structured to match Godot idioms — autoload singletons, signal bus, Resource-based data, painter's sort by depth. Most files port 1-for-1.

Architecture overview

The Godot project follows the same shape as the JS prototype but uses native Godot idioms wherever they're stronger: autoload singletons for global state, Resources for data authoring, signals via an EventBus to keep systems decoupled, and a TileMapLayer for the iso ground.

Why this shape

The JS used window.X globals because there are no modules. Godot's autoloads are the exact same idea but native, hot-reloadable, and inspector-visible. The Resource-driven authoring means designers can add a new weapon by duplicating a .tres and tweaking fields — no code touched.

File index

What you'll find when you open godot/ in the editor:

project.godot
Engine config: window size, autoloads, input map (WASD, MB1/2, E, TAB, C, 1–5), render layers. Drop the folder onto Godot's Project Manager and it'll pick this up.
scripts/IsoMath.gd
Static helpers: world_to_screen, screen_to_world, cursor_facing, in_arc (the directional-swing check), raycast_hit (for ranged weapons). No state.
scripts/autoload/EventBus.gd
Global signal hub. Emit from anywhere, listen from anywhere. Keeps Player ↔ HUD ↔ Inventory decoupled.
scripts/autoload/GameState.gd
Time of day, day counter, phase enum, darkness curve, illuminate timer. Drives the day/night cycle.
scripts/autoload/Inventory.gd
Player's pack: 32 slots, equipment dict (weapon/armor/shield/accessory), 5-slot hotbar with -1 sentinel for "equipped weapon". API mirrors the JS module exactly.
scripts/autoload/Database.gd
Loads all .tres files at startup and exposes Database.item(&"rusted_sword"). No more hard-coded item IDs.
scripts/Item.gd · WeaponItem.gd · Recipe.gd · EnemyData.gd
Resource classes. Each one corresponds to a category of .tres file. Editor-friendly with @export groups.
scripts/Player.gd
CharacterBody2D script. Mirrors the JS player: WASD → iso velocity, mouse facing, click-attack with arc (or raycast for ranged), stamina/mana/hunger/thirst decay, iframes, blocking with shield, death.
scripts/Enemy.gd + scripts/AI/*.gd
Base enemy class delegates per-frame decisions to its AI module (Strategy pattern). Skeleton (wander+chase), Wraith (ghost+drift), Ghoul (telegraph+swing). Add a new variant by writing a new AI script + EnemyData.tres.
scripts/WorldGen.gd
Builds the 60×60 world at _ready: fills the TileMapLayer, carves the road, places cemetery/pond/houses, scatters props, spawns enemies. Seedable for repeatability.
scripts/HUD.gd
CanvasLayer controller. Listens to EventBus and updates bars, clock, hotbar, log, prompt. Hides hunger/thirst/mana when not relevant.
scripts/DayNight.gd
CanvasModulate script. Reads GameState.darkness() each frame and tints the world toward cold moonlight.
scripts/Prop.gd · Container.gd
Static-body scenery. Damage-able. Containers extend Prop with loot + opened for chests/barrels/cars.
resources/items/*.tres
6 starter items as templates: Rusted Sword, Silver Dagger (with bonus-vs-wraith), Oak Staff (mana cost), Service Pistol (ammo), Bandage (consumable), Rag (material). Duplicate one to make new weapons.
resources/enemies/*.tres
Skeleton, Wraith, Ghoul with stats and AI script bound. Adding a new enemy = new EnemyData.tres pointing at a new AI script.
resources/recipes/*.tres
Bandage recipe as a template (3 Rags → 1 Bandage). Add more by referencing other Item .tres files.
SCENE_TREE.md
Text blueprint of Main.tscn — the scene tree you need to build in the editor. Node names match @onready references in the scripts.

Setup steps

  1. Open the folder in Godot 4.3+

    Launch Godot, click Import, point at the godot/ folder, and let it scan. Autoloads register automatically from project.godot. You'll see four scripts at the bottom of the Scene panel: GameState · Inventory · Database · EventBus.

  2. Build the TileSet for the ground

    Create a 64×32 isometric TileSet. Add 11 atlas sources matching the Tile enum in WorldGen.gd: grass, grass_dark, moss, dirt, road, road_edge, sidewalk, floor_wood, floor_tile, water, grave. Use solid color rects to start — swap to real sprites later. Place a TileMapLayer in your scene with this TileSet, mode = Isometric.

  3. Create Player.tscn

    CharacterBody2D root → attach Player.gd → add child Sprite2D ("Sprite"), Sprite2D ("WeaponSprite"), CollisionShape2D ("Collision", capsule ~24×12), Camera2D ("Camera", current = true), Node2D ("AimIndicator"). Add to group player in the inspector.

  4. Create Enemy.tscn

    CharacterBody2D → Enemy.gd → assign data to one of the EnemyData .tres files. Children: Sprite (placeholder), Collision, and an empty Node called "AIHost". The base script applies the AI script automatically from data.ai_script. Add to group enemy.

  5. Create prop scenes

    One scene each for Tree, DeadTree, Gravestone, Car, Barrel, Crate, Chest, Fence. Either StaticBody2D + Prop.gd (or Container.gd for loot ones). Sized 1×1 tile collision footprint. Add to group prop.

  6. Build Main.tscn

    Follow the tree blueprint in SCENE_TREE.md. Drop a WorldGen node in and assign all the @export PackedScene fields to your scene files. The TileMapLayer + Structures/Props/Enemies/Drops Node2Ds get assigned to the WorldGen too. Add WorldGen to group world_gen.

  7. Build HUD.tscn

    CanvasLayer with the children listed in SCENE_TREE.md. Use Control + ColorRect for the stat bars (HUD.gd drives anchor_right for the fill). RichTextLabel for the log with BBCode enabled. Hotbar = HBoxContainer with five PanelContainers.

  8. Equip starting items

    In Main.gd's _ready, add starter items: Inventory.add(Database.item(&"rusted_sword"), 1), equip them, set hotbar slot 0 to -1 (sentinel). Same pattern as the JS prototype's game.js startup block.

  9. Run it

    F5 to play. WASD moves, mouse aims, LMB attacks in the cursor direction. The HUD updates from the EventBus.stats_changed signal each frame. Sleep, eat, swing, survive.

Deep dives

Directional attack arc

In the JS prototype, each click computes the angle from player to cursor in world space, then for every enemy: check distance ≤ range, check angular delta ≤ arc/2. If both true → hit.

In Godot, this lives in IsoMath.in_arc(origin, target, facing, range, arc). Player.gd calls it across the enemy group on each click. No physics shape — pure math. This is faster than swept hitboxes and trivially extends to wider/narrower weapon arcs.

Painter sort for occlusion

Iso rendering needs back-to-front draw order. In JS we sorted by wx + wy each frame. In Godot 4, set y_sort_enabled = true on the parent Node2D and Godot does it automatically. For tiles, the TileMapLayer y-sorts within itself.

For sprites whose center-of-mass doesn't match their feet, set z_index manually to int(tile.x + tile.y). WorldGen.gd does this when instancing props.

Resource-driven content

In JS, adding a weapon meant editing items.js. In Godot, you duplicate rusted_sword.tres, change the fields in the Inspector, save under a new name. Database picks it up at startup.

This is the single biggest authoring win. Designers, modders, and tools can all create content without touching code.

AI as composable strategies

Each enemy archetype is an EnemyData.tres + a paired AI script. The base Enemy.gd handles physics and damage; the AI script implements ai_tick(enemy, delta).

To add a Necromancer: write NecromancerAI.gd with a tick that summons skeleton scenes on cooldown, save necromancer.tres pointing at it. No subclassing required.

Decoupled HUD

The HUD only reads from EventBus signals — never reaches into the Player node. When the Player loses HP, it emits player_hurt; HUD listens and updates the bar and triggers the hurt flash tween.

This means audio, screen shake, controller rumble, or accessibility readouts can all hook the same signals without touching combat code.

Day/night as a curve

GameState.darkness() returns 0..1 based on hour-of-day. CanvasModulate lerps its color toward a cold-blue night tint each frame. Spell-of-Light just sets a timestamp that the darkness function multiplies by 0.2 until expiry.

For real shadow casting later, swap CanvasModulate for a WorldEnvironment 2D or a CanvasItemMaterial shader with point lights.

Gotchas & design notes

Iso velocity is screen-space

In Player.gd, WASD produces a tile-space direction, then IsoMath.world_to_screen(dir) * speed converts to pixels/sec for move_and_slide(). If you skip the conversion the player will drift diagonally in the wrong direction. Don't refactor this without keeping the iso transform.

Wall collision needs collision polys, not just floor tiles

The JS prototype fakes wall collision by checking distance from each structure's wall edges. In Godot, give each house scene actual StaticBody2D children for its four wall segments, with a gap for the door. Cleaner than ported edge-checks and free physics.

TileMapLayer (4.3+) vs TileMap (4.2)

WorldGen.gd is written against the newer TileMapLayer. If you're on 4.2, swap to TileMap and adjust the set_cell calls (add a layer argument).

Drop spawn currently emits a placeholder signal

Enemy.gd's _drop_loot stub needs a Drop scene to instance. Create scenes/Drop.tscn (Area2D + Sprite2D + a tile_pos, item, qty) and have WorldGen.spawn_drop instance it. The commented line in the script shows the call site.

Ranged VFX

Player._ranged_shoot currently resolves damage instantly without a visible projectile. For bullets/arrows/spell bolts, spawn a Line2D child that tweens its alpha over ~90ms. For spell bolts make it violet (mana hue from the prototype palette).

Newer systems

These were added after the initial handoff. Same idioms — Resources for data, signals for cross-system events, AI as composable modules.

Enemy variety + faction-based targeting

The prototype now has six enemy archetypes split across two factions, plus civilians as a third faction. Targeting is driven by a hostility matrix — each entity picks the closest target whose faction is on its hostile list.

FACTION MEMBERS TARGETS
monster skeleton, wraith, ghoul, cultist player + human_hostile + civilian
human_hostile bandit, guard player + monster + civilian
civilian NPCs — (flees instead of attacks)
player you explicit click only
Godot port — Faction resource + targeting

Add a Faction.gd Resource with an @export var hostile_to: Array[StringName]. Each enemy's EnemyData.tres gets a faction field pointing at a Faction. In Enemy.gd, replace the direct player reference with a find_target() helper that scans the player, enemy, and civilian groups for the closest hostile. The AI modules call find_target() once per tick instead of hardcoding e.player.

New enemy archetypes

cultist.tres
28 HP, magic caster. Stays at 7-tile range, fires cold-flame bolts (16 dmg, 1.8s CD). Charges glowing fingertips before each cast. Drops wraith ash + occasional mana potion.
bandit.tres
55 HP, pistol + 8 starting rounds. Maintains ~4.5-tile distance. Out of ammo: 55% chance to flee, else draws a knife. Drops pistol rounds.
guard.tres
95 HP, shotgun + 6 shells (heavy spread). Holds ~3-tile range. Never flees — out of ammo means draws a longblade and charges. Drops shells + sometimes chainmail.
Godot port — ammo + fallback AI

Extend EnemyData with: ranged_dmg, ranged_range, ranged_cooldown_ms, start_ammo, flee_when_out_chance, has_melee, keep_distance_tiles. The AI module (e.g. BanditAI.gd) decides on the first frame after ammo hits zero — flee vs draw a blade. Store the decision in e._ammo_decision_made so it sticks. For the shot itself: spawn a Line2D between enemy and target with a tween that fades alpha to zero in ~110ms.

Civilians + dialogue

Civilians are a separate node group, not enemies. They wander a home radius, flee from hostile factions within sight, and can be talked to with E. Each carries a name, a role ("baker", "caretaker", "fisher"…), and a few dialogue lines.

Civilian (CharacterBody2D) [Civilian.gd]     @group: civilian
├── Sprite / Model3D            ; 2D placeholder or 3D model
├── Collision
├── DialogueComponent           ; holds lines + name + role
└── FleeBehavior                ; computes flee vector from hostile groups

Dialogue UI is a CanvasLayer panel (Control) anchored bottom-center. Clicking or pressing SPACE advances; the last line closes. While open, the player's attack input is gated.

Godot port — dialogue Resource

Create Dialogue.gd Resource with @export var npc_name: String, @export var role: String, @export var lines: PackedStringArray. Each civilian scene exports a Dialogue resource. A global DialogueController.gd autoload manages the open/advance/close state and emits EventBus.dialogue_opened / dialogue_advanced / dialogue_closed.

Building lighting + window glow

Each structure gets a lit boolean at world-gen (~45% chance). Lit buildings render warm amber window panes; dark buildings render cold-blue panes. A "light switch" prop next to each entrance toggles the state with E.

Godot port — per-building light

Each House.tscn instance has a lit property and a child WindowLights Node2D holding Light2D emitters at each window. Toggle WindowLights.visible based on lit. The light switch is a separate scene that exports the parent house ref and toggles it on E. Use Light2D.energy tweens for the flicker-on effect.

Vision cone in dark interiors

When the player is inside an unlit building, a fullscreen dark overlay covers everything except a ~70° cone forward of the player's facing, plus a tiny halo at the feet. Cone direction is computed in screen-space (the world-facing angle is iso-projected).

Godot port — vision cone via Light2D

This is the cleanest 2D Godot pattern: a CanvasModulate over the whole scene set to near-black when the player is in a dark structure, and a child Light2D on the player with a custom cone-shaped texture (an alpha gradient inside a wedge). Energy and rotation track player.facing. For 2D inside a 3D character setup, use a Light3D SpotLight on the player and an unlit ambient when inside dark buildings — same idea, native primitives.

Doors — open/close + multi-room buildings

Every house has a main door on its south wall; bigger houses also have an interior dividing wall with an interior door. Both start closed, block movement when closed, and toggle with E when the player is adjacent. The prompt updates ("Open door" / "Close door") based on state.

House (Node2D)
├── Floor (Sprite2D / TileMap chunk)
├── Walls (Node2D)
│   ├── NorthWall (StaticBody2D + CollisionShape2D)
│   ├── SouthWall (broken by door gap)
│   ├── EastWall · WestWall
│   └── InteriorWall (optional, also broken by interior door)
├── MainDoor (Area2D + Sprite + Collision) [Door.gd]
├── InteriorDoor (optional)
├── LightSwitch (Area2D) [LightSwitch.gd]
├── WindowLights (Node2D w/ Light2Ds)
└── lit: bool, interior: bool        ; @exports on House.gd
Godot port — door interaction

Each Door.gd exposes is_open: bool and a toggle() method. Use an Area2D for proximity detection (body_entered sets the player's nearest_door); on E, the player calls nearest_door.toggle(). CollisionShape2D's disabled property toggles in lockstep with is_open so movement clears the gap when open.

3D characters in a 2.5D world

The world stays 2D (TileMapLayer iso). Characters become 3D models in a parallel Node3D scene, rendered via a SubViewport composited over the 2D world, OR you go fully 3D with an orthographic camera angled to mimic iso.

Two viable mixing strategies

Option A — 2D world + Sprite3D characters (recommended for prototypes): Keep the TileMapLayer scene. Render characters as Sprite3D nodes with billboarding off (so they rotate naturally), or as full MeshInstance3Ds, inside a SubViewport. Composite the viewport's texture onto the 2D scene via a SubViewportContainer. Cheap to set up, looks great with iso.

Option B — Fully 3D scene with orthographic camera: Build the world as a flat 3D plane with TileMap-style instancing of tile meshes. Use a Camera3D in orthographic mode at the iso angle (atan(0.5) pitch, 45° yaw). Characters are 3D models in the same scene. Heavier but unifies everything — better for production.

Faction combat — humans fighting monsters

Because targeting is faction-driven, bandits and guards now shoot at skeletons/wraiths/cultists in line of sight, and monsters maul humans. The player can stand back and watch a firefight resolve. Civilians caught in the middle die quickly — they're fragile and don't fight back.

Godot port — group-based combat

Add each entity to the right Godot group: add_to_group("monster"), add_to_group("human_hostile"), add_to_group("civilian"). The find_target() helper iterates the relevant groups using get_tree().get_nodes_in_group() instead of a single player reference. Apply damage through a shared Damageable interface (a script that all damage-takers extend, or a duck-typed take_damage(amount, source) method).
